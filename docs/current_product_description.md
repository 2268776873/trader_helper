# Trade Helper 当前产品说明

版本：当前产品阶段
更新日期：2026-08-03

## 1. 产品是什么

Trade Helper 是一个本地运行的低频 ETF 仓位管理决策助手。它根据用户真实账户状态、已发生的交易、策略运行状态和当日市场数据，生成可复核的买入、卖出或不操作建议。

产品不连接券商自动下单，也不预测短期涨跌。用户仍在券商客户端人工下单，并把实际成交结果回填到产品中。

这里的“即时建议”是指：账户或市场数据更新后，用户运行决策即可按最新数据重新计算。当前产品不是连续监听行情、自动推送订单的实时交易系统；正常使用频率是交易日内按计划运行一次，必要时在修复数据或账户状态后重新运行。

## 2. 产品使用哪些信息

一次决策主要读取以下信息：

1. **最新账户快照**：总资产、可用现金、冻结现金，以及三只 ETF 的持仓数量和券商市值；
2. **最新快照之后的真实成交**：只采用状态为 `FILLED` 的买卖成交，用来把快照推演到当前仓位和现金；
3. **交易历史形成的策略状态**：已完成的回撤档位、各档位累计成交额、基础预算释放情况、虚拟资金池余额和持续超配天数；
4. **当日市场数据**：卖一价、买一价、至少两路估值、数据时间和数据质量状态；
5. **历史参考序列**：用于计算各资产相对最多 250 个已读取交易日高点的回撤；
6. **交易日历和当前策略配置**：用于月度预算释放、交易日判断、权重、阈值和风控限制。

“交易历史”不是简单作为一个特征参与打分。它有两个明确作用：一是将最近账户快照更新到当前真实账户状态；二是通过真实成交推进资金池、回撤档位和再平衡状态。当前策略不根据历史持仓成本或历史盈亏预测未来价格。

## 3. 账户状态如何得到

系统先选取时间最新的账户快照，以快照中的总资产、现金和各资产市值作为基线。

然后依次叠加快照时间之后所有已确认成交：

- 买入：现金减少，相关资产市值增加；
- 卖出：现金增加，相关资产市值减少；
- 未操作、仅提交委托、撤单和未成交记录：不改变账户状态；
- 部分成交：只按实际回填的成交数量和价格计入。

推演后必须满足：

```text
现金 >= 0
每项资产市值 >= 0
现金 + 三项资产市值 = 账户总资产
```

不满足时账户进入未对账状态，系统不会生成可执行建议。

## 4. 交易建议如何计算

系统先做安全门检查，再按策略优先级计算。当前规则不是黑箱评分模型，而是可审计的确定性规则。

### 4.1 安全门

出现以下任一情况时，建议会被阻断：

- 账户快照缺失或账面无法对平；
- 市场快照缺失、过期或关键数据源未达到 `READY`；
- 缺少可执行盘口价格或两路估值；
- 两路估值对应的折溢价差异超过配置阈值；
- 当日已经存在成功决策，或存在其他策略和执行状态限制。

### 4.2 回撤加仓

每只资产用历史参考序列计算当前回撤，并与该资产尚未完成的回撤档位比较。

满足新档位后，可买金额受以下条件共同限制：

- 该档位剩余计划金额；
- 对应回撤资金池余额；
- 当日买入上限的剩余额度；
- 当前现金减去战略现金底线后的余额；
- 该资产距离最大允许权重的空间；
- ETF 折溢价限制和最高允许买价。

多个档位同时满足时按冻结策略规定的档位顺序处理。档位只有实际成交后才累计完成，生成建议或提交委托本身不会消耗档位预算。

### 4.3 基础建仓

基础预算按配置的月份和交易日释放。系统计算三项资产的欠配金额：

```text
欠配金额 = 总资产 × 目标权重 - 当前资产市值
```

候选资产按欠配金额从大到小排序，从数据合格、仍有权重空间且折溢价合格的资产中选择。建议金额同时受基础池余额、月度执行上限、当日买入上限、现金底线、欠配金额和最大权重空间限制。

回撤加仓优先于基础建仓；回撤建议占用当日额度和现金后，基础建仓只能使用剩余额度。

### 4.4 卖出再平衡

资产严重超配、连续多个交易日高于最大权重，或标普/纳指出现极端 QDII 溢价且权重高于目标时，可以触发卖出建议。

- 一般持续或严重超配：卖回最大允许权重；
- 极端 QDII 溢价：卖出超过目标权重的部分；
- 实际卖出所得：成交后进入战略现金，不自动触发另一笔买入。

### 4.5 数量和价格

买入使用合格卖一价，卖出使用合格买一价。数量按 100 份整手向下取整，不追价；取整后低于最小订单金额则不生成订单建议。

最终建议会保存方向、标的、触发类型或档位、建议数量、限价、金额和原因。没有合格机会时输出“不操作”或具体阻断原因。

## 5. 数据更新后是否会影响建议

会，但不同数据的生效方式不同：

| 用户变化 | 推荐写入方式 | 对下一次建议的影响 |
|---|---|---|
| 当前总资产、现金、持仓变化 | 新增一组账户与持仓快照 | 作为新的账户基线，重算权重、欠配和现金空间 |
| 实际买卖成交 | 回填成交或 Excel 导入 | 更新快照后的仓位和现金，并推进档位及资金池状态 |
| 资金转入或转出 | 客户端“存取现金” | 在同一事务中更新账户快照、现金流水和资金池 |
| 批量历史数据 | Excel 预检查后导入 | 原子写入快照、成交和资金流水，重复批次不会再次导入 |
| 市场行情变化 | 重新采集市场数据 | 更新价格、折溢价、回撤和可交易性判断 |

建议重新运行后才会重新计算。已保存的历史建议不会因后来修改数据而被静默改写。

## 6. 能否直接修改 SQLite 数据库

从技术上可以，因为账户、成交、资金流水和策略状态都保存在本地 SQLite 数据库中；但“直接修改数据库”不是产品级数据维护接口，也不等于只改一个字段就能安全生效。

相关信息分布在多组相互关联的数据中：

- `account_snapshots` 与 `position_snapshots`：账户基线和持仓；
- `trades`、`advice_fills`：真实成交及其建议关联；
- `cash_flows`、`cash_pool_events`：资金流水和虚拟资金池变动；
- `strategy_runtime`、`tactical_level_state`、`rebalance_state`：策略运行状态；
- `decision_runs`、`advice`：历史决策和建议审计记录。

直接改库可能绕过金额单位转换、外键、唯一性、幂等、资金池守恒、档位推进和审计记录。例如只修改现金快照，不同步资金流水和资金池，下一次建议虽然可能读到新的现金，却可能使用旧的预算状态；只插入成交而不通过成交回填流程，也可能使持仓推演与档位状态不一致。

因此产品支持的更新顺序是：

1. 日常少量变更使用客户端的账户更新、存取现金和成交回填功能；
2. 初始化或批量补录使用标准 Excel 模板，经预检查后原子导入；
3. 只有故障修复或数据迁移才直接操作数据库，并应先创建校验备份、在事务中修改、检查关联状态，最后运行完整性和账户对账检查。

换言之，数据库能够承载这些变化，但产品应通过受控写入流程支持它们，而不是把手工 SQL 当成正常操作入口。
## 7. 当前产品边界

- 只管理冻结策略配置中的三只权益 ETF 和策略现金；
- 账户和交易数据保存在本地，不保存券商密码或验证码；
- 市场数据自动采集，用户主要维护真实成交、存取款和账户变化；
- 建议与成交严格分离，只有真实成交改变仓位、现金池和档位状态；
- 当前是规则化建议系统，不是收益预测、自动交易或通用证券组合优化平台。
